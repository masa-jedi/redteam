01

Start high. Then go deeper.

Three readings of the same result. Read the first column, then the second, then the third.

10 seconds

The lab is exploitable. A crafted multipart body OOMs a PHP 8.4.26 worker, leaks the heap and a code pointer, forges a cleanup callback, and runs a command. Four verified runs; the flag is synthetic. The real site was not touched.

5 years old

A robot clerk has a tiny desk. You give it a giant form; it runs out of desk space and drops its notes. The notes tell you where its desk and rulebook are. You hand it a fake card, and it reads the card instead of the rulebook. That is the whole trick.

Engineer

PHP 8.4.26, Alpine CLI server, 4 workers, nginx in front, memory_limit=128M, upload progress on. 249 KiB producer → OOM → stale session state. 8 consumers → 256-byte PHPSESSID → heap chunk 0x783213000000. Second pair → 16-byte cookie → zval_ptr_dtor low21 0x112930. Forged 384-byte HashTable → zif_system → command writes to the upstream socket. Success is a race: ~4/10 here, 7/10 upstream.

02

The hotel story.

A real-world narrative first. The mapping to the technical objects is underneath.

Heap = the desk

The place where the program keeps its working papers: the form data, the session, the fake card. The 128 MiB memory limit is how big the desk is.

Cookie = the note the clerk hands back

A website gives your browser a small note and asks it to bring it back next time. The server writes Set-Cookie: PHPSESSID=...; the browser returns it. The cookie is the envelope; the number on the sticky note is a number that tells you where the desk is.

Imagine a hotel with a very fast robot clerk. The clerk reads forms all day and keeps its notes on a small desk beside it. The desk is only so big. The clerk also has a rulebook and a master key.

  1. The giant form. You hand the clerk a form with a thousand tiny boxes inside boxes. It tries to open every box at once. The desk fills up, the clerk runs out of space, and it drops its notes on the desk. It keeps working.

  2. The dropped notes. You hand it eight more small forms very quickly. One of the dropped notes is a note the clerk hands back; stuck to it is a sticky note with a number that says where the desk is.

  3. The rulebook. You hand it another giant form. It drops a different note: a number that says where the rulebook is kept.

  4. The fake card. You now know where the desk is and where the rulebook is. You hand the clerk one last form with a fake instruction card. While cleaning up, the clerk reads the card instead of the rulebook, and does what it says.

  5. The golden ticket. The fake instruction says “print the golden ticket.” The clerk writes it onto the reply it was already sending back. That is the flag. In our hotel, the golden ticket is fake and there are no real guests.

03

The lab, high level.

Four services, one internal network, no route to the internet. nginx is the front desk; the PHP CLI server is the clerk pool; the attacker is the visitor; telemetry watches the wire.

The critical detail: the PHP worker owns the upstream socket to nginx, not the client socket. That is why the command output reaches the HTTP response.

The real-world version

A hotel with a robot clerk and a master key. The clerk is a PHP worker; the desk is the heap; the forms are multipart requests; the dropped notes are cookies; the rulebook is the code image; the fake card is a forged cleanup callback. 04

The bug and the gain.

Not an application bug. Not a wallet. A memory-corruption chain in PHP's request parser, reached through a crafted multipart body.

What the bug is. PHP 8.4.26 parses a multipart body into deeply nested arrays while it is also handling session upload progress. On this build, with a 128 MiB limit, the parse exhausts memory. The OOM leaves half-built session state in a worker that is then reused. The PoC turns that state into two disclosures and a forged PHP structure.

STAGE 01

Exhaust

A 249 KiB body with nested names builds a tree much larger than the wire bytes. The 128 MiB limit is hit; the worker survives with stale state.

STAGE 02

Leak heap

Eight consumers race for the poisoned worker. One returns a 256-byte PHPSESSID; the pointers agree on a 2 MiB-aligned chunk base.

STAGE 03

Leak code

A second pair returns a 16-byte cookie with zval_ptr_dtor. Its low 21 bits, 0x112930, are the build fingerprint.

STAGE 04

Callback

A 384-byte forged HashTable points pDestructor at zif_system; cleanup calls it with the command in the same buffer.

What the hacker gains

Remote code execution as the worker. In this lab that is root inside the container; it can read /flag and anything the PHP process can reach. The response also carries the execution proof: a fresh nonce, uid=, the print-flag hash, and the flag. The successful callback also kills the CLI server parent (Exited (139)) — an availability side effect, not a separate exploit.

What it is not. Not an application bug (the app is six lines). Not a configuration mistake (the lab is deliberately hardened: internal network, read-only root, cap_drop: ALL, no published port). Not a generic PHP exploit: the heap and code offsets are specific to this Alpine build, four workers, 128 MiB, and nginx. The exact source-level root cause in PHP's parser is the PoC author's claim; this task reproduced the behavior, not an independent C-level root cause.

The honest part

Blind? No. The blind phase produced the OOM and rejected Apache/direct CLI; the CLI+nginx design came from the unsealed writeup. The final success is a reproduction of the documented lab, not a blind discovery. Reliable? No. About 4/10 base attempts here; the writeup reports 7/10; the callback can miss. Independent? Partially. The flag/byte oracles are independent of the exploit path; GLM-5.3 agreed on the core but time-boxed C3/C8/C9.

06

The scan, and its checklist.

A scan reads the sign on the door. An attack tries the lock. The sign can say PHP/8.4.26 and still hide the build; the exact build is only visible after the leak.

The five-year-old version

Before you knock on a thousand doors, look at the sign. Does it say “PHP 8.4.26”? Is there a little door called php-version.php? That tells you the hotel might have the right clerk. It does not tell you the clerk can be tricked. Reading the sign is a scan. Pushing the clerk over is the attack. Do not push a thousand clerks.

Scan ≠ attack

A scan is 2–5 light requests; a confirmation is the 9-request OOM chain. The exact build, upload-progress setting, worker count, and heap are not visible from outside. The version header is a candidate; the lab (make verify) confirms the class; the target confirmation is an authorized exploit or an owner-assisted staging run, not a scan. For 1,000 arbitrary sites: use passive data, not 1,000 live probes; and do not run 1,000 exploit attempts. Authorization is the gate.

The internet arguments.

Two tweets, one shared fact, two different conclusions. The static page was a real deployment mistake; it is not proof that the bug is unexploitable or that the challenge was bad-faith.

What is actually true

The static-file diagnosis is the strongest part of both tweets. The architecture is nginx → PHP CLI server. The bug is real and exploitable in the calibrated lab. The deployment had a real mistake; the challenge is a PoC for the exploit, not a debunk. The “unexploitable” crowd is wrong; the “AI solved it from nothing” crowd is also overclaiming. The AI reproduced a public PoC after the lab was specified.

08

Agents and swarms: necessary?

Not for this execution, and not for this scan. One operator plus one independent verifier is enough. A swarm is for breadth, not for a single racy exploit.

JobOne agent enough?Swarm needed?Why
Read the PoC and write hypothesesYesNoOne 763-line file; the hypotheses are serial
Build the labYesNoEnvironment work is one bottleneck at a time
Find the right server classYesMaybeThe Apache/direct-CLI failures were serial hypotheses; small space
Run the exploitYesNoOne script against four workers; multiple attackers contend and confuse the race
Independent verificationNo (producer cannot)One verifierA swarm of verifiers adds correlated opinions, not independence
Scan the app with the starter stackIrrelevantNoThe bug is in the PHP runtime, not the app/dependencies
Future breadth (many endpoints, fuzzing, hosts)NoYesThat is where parallel workers pay off

Good at

Repetitive evidence checks, reading many files, building the lab, trying alternative hypotheses, writing the handoff.

Bad at

Being independent of themselves, resisting a confident wrong hypothesis, and coordinating a race that needs one attacker.

The rule of thumb

Use a swarm when the work is parallel and independent; use one operator plus one verifier when the work is a single exploit.
